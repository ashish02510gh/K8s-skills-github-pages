etcd Overview

etcd is the distributed key-value store that holds all cluster data. Securing etcd is critical because it contains sensitive information like secrets, credentials, and the entire cluster state. Unauthorized access to etcd means complete cluster compromise.

🔴 Critical: etcd is the most sensitive component in a Kubernetes cluster. It must be protected with the highest priority.

Encryption at Rest

Enable Encryption Provider

Configure API server to encrypt secrets before storing in etcd:

--encryption-provider-config=/etc/kubernetes/encryption-config.yaml
--encryption-provider-config-automatic-reload=true

Encryption Configuration

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: rWtsy+O4008S2Z5+DcjokQ==
  - identity: {}

Using KMS Plugin

providers:
- kms:
    apiVersion: v1
    cachesize: 1000
    endpoint: unix:///var/run/kmsplugin/socket.sock
    timeout: 3s

Secure Communication

Peer Communication

  • Enable TLS for peer-to-peer communication
  • Use peer certificates (etcd-peer.crt/key)
  • Verify peer certificates

Client Communication

  • Enforce TLS for client connections
  • Require client certificates
  • Validate client certificates

Configuration

# etcd server flags
--cert-file=/etc/kubernetes/pki/etcd/server.crt
--key-file=/etc/kubernetes/pki/etcd/server.key
--peer-cert-file=/etc/kubernetes/pki/etcd/peer.crt
--peer-key-file=/etc/kubernetes/pki/etcd/peer.key
--peer-client-cert-auth=true
--client-cert-auth=true

Access Control

Authentication

  • Only API server should access etcd
  • Use service accounts for authentication
  • Restrict network access to etcd

Network Isolation

  • Place etcd on internal network only
  • Restrict firewall rules to control plane nodes
  • Use separate subnet for etcd

Backup Protection

  • Encrypt backups
  • Store in secure location
  • Limit access to backup files
  • Test backup restoration regularly

Backup Strategies

Regular Backups

# Backup etcd data
etcdctl snapshot save /backup/etcd-backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

Verification

# Verify backup integrity
etcdctl snapshot status /backup/etcd-backup.db

Automated Backups

  • Use CronJob to backup regularly
  • Backup frequency: daily minimum
  • Retention: keep 7-30 days
  • Store in multiple locations (on-premise + cloud)

Disaster Recovery

Restore from Snapshot

# Restore etcd from snapshot
etcdctl snapshot restore /backup/etcd-backup.db \
  --data-dir=/var/lib/etcd-restored

# Replace etcd data directory
sudo mv /var/lib/etcd /var/lib/etcd-old
sudo mv /var/lib/etcd-restored /var/lib/etcd

# Restart etcd
sudo systemctl restart etcd

Testing Restores

  • Test restore procedures regularly
  • Practice in staging environment first
  • Document recovery procedures
  • Time the recovery process

Best Practices

  • ✓ Always encrypt data in etcd using KMS
  • ✓ Enable TLS for all etcd communications
  • ✓ Restrict network access to etcd (control plane only)
  • ✓ Implement daily backups
  • ✓ Store backups in multiple locations
  • ✓ Test restoration procedures monthly
  • ✓ Keep backup encryption keys separate
  • ✓ Monitor etcd disk usage and performance
  • ✓ Enable etcd audit logging
  • ✓ Implement defragmentation schedule
